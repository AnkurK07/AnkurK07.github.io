vLLM

vLLM

UC Berkeley, 2023 · Apache-2.0 · github.com/vllm-project/vllm

When you call a large language model, the GPU must store the intermediate attention state — Key-Value (KV) cache — for every token in every active sequence. Naively, this wastes 60–80% of GPU memory to fragmentation and over-reservation. vLLM was the first system to treat GPU memory like a virtual-memory OS, unlocking massive batch sizes and dramatically higher throughput.

PagedAttention — The Core Innovation

Classical serving pre-allocates a contiguous memory block for each request's KV cache — sized for the maximum possible sequence length. Since most sequences end much sooner, this wastes enormous memory. PagedAttention partitions the KV cache into fixed-size blocks (pages), exactly like virtual memory in an OS, and maps them non-contiguously with a block table.

PagedAttention — Block Table Memory Model
Why this matters: Traditional serving wastes 60–80% of GPU memory on reserved-but-unused KV cache. PagedAttention reduces this waste to under 4%, enabling the GPU to serve 10–24× more concurrent requests for the same hardware. Copy-on-Write semantics also enable free prefix sharing across parallel beams.

Continuous Batching

Static batching waits for the entire batch to finish before loading new requests. Since sequences have wildly different lengths, GPUs idle waiting for the last slow sequence. Continuous batching inserts new requests immediately after any sequence in the batch completes, keeping the GPU saturated at all times.

Static vs Continuous Batching — GPU Utilization Timeline
KV Cache Memory Manager

A central allocator tracks free physical blocks across the GPU. When a new token is generated, a block is assigned if the current one is full. Blocks from finished sequences are instantly reclaimed — like garbage collection but for attention state.

Copy-on-Write for Beam Search

Multiple beams can share the same physical KV blocks until they diverge. Only when a beam writes a new token does the system copy the block — eliminating redundant memory for parallel decoding strategies like beam search or speculative decoding.

Prefix Caching

vLLM can cache KV blocks of common system prompts. If 1000 requests share the same system prompt, the GPU computes its KV cache once and reuses the physical blocks across all requests — saving compute and time on every repeated prefix.

Tensor + Pipeline Parallelism

vLLM's distributed runtime uses Ray or custom NCCL backends to shard model weights across multiple GPUs via tensor parallelism (splitting within a layer) and pipeline parallelism (splitting across layers), enabling models larger than a single GPU's VRAM.

SGL

SGLang

Stanford, 2024 · Apache-2.0 · github.com/sgl-project/sglang

Most real LLM applications aren't single-turn — they call the model multiple times, chain prompts, fork branches, or enforce structured output formats like JSON. vLLM optimizes individual calls. SGLang introduces a structured generation language and a smart runtime that understands the entire program, making multi-call LLM programs orders of magnitude faster through aggressive prefix reuse and kernel-level structured generation.

RadixAttention — KV Cache as a Radix Tree

Where vLLM hashes individual prompts for prefix caching, SGLang builds a Radix Tree (a compressed trie) over all KV cache content. Every node represents a shared prefix. When a new request arrives, the tree is traversed to find the longest matching prefix, and only the new suffix needs computation. Eviction follows an LRU policy across the tree.

RadixAttention — Prefix Sharing via Radix Tree
RadixAttention vs vLLM prefix caching: vLLM only hashes the exact prefix string. SGLang's Radix Tree finds the longest matching prefix even when prompts share partial overlaps of different lengths. This makes it dramatically better for multi-turn conversations, few-shot chains, and batch inference with slight prompt variations.

Structured Generation & the SGL Language

SGLang exposes a Python DSL where fork(), gen(), and select() primitives are compiled by the runtime into optimized CUDA execution plans. The runtime understands parallelism across forks, batches them, and reuses the shared prefix KV cache across all branches.

SGLang Structured Generation — Runtime Execution Plan
"You are…") s += sgl.user(question) s += sgl.gen("answer") forks = s.fork(3) forks += sgl.gen("critique") s += forks.join().gen("final") # 3 parallel critique branches → RUNTIME EXECUTION GRAPH Prefill: sys + user KV stored → radix node gen("answer") [decode] fork(3) — Copy-on-Write critique A critique B critique C join() + gen("final") ✓ All 3 critiques run BATCHED (1 GPU pass) ✓ Shared prefix KV computed once for all forks → 6.4× faster than sequential chaining in vLLM
Constrained Decoding (xGrammar)

SGLang integrates xGrammar for blazing-fast JSON schema and regex-constrained decoding. Instead of filtering logits at each step, it pre-compiles grammar masks, letting the GPU enforce structure at near-zero overhead. This is essential for reliable tool-calling and structured extraction.

Jump-Forward Decoding

When constrained generation requires fixed strings (like JSON keys in a schema), SGLang skips sampling entirely and jumps the token pointer forward — filling in deterministic tokens without invoking the decoder at all. This eliminates unnecessary compute for required tokens.

ChunkPrefill

Long context prompts are chunked and prefilled in parallel segments rather than as a single blocking prefill, preventing the GPU from stalling on one giant prefill while other decode requests wait. Dramatically improves TTFT (Time To First Token) under load.

Disaggregated Prefill

SGLang can route prefill computation to dedicated "prefill workers" and decode computation to "decode workers", splitting the GPU fleet by workload type. This avoids the prefill-decode interference that plagues unified serving systems under mixed load.

TRT

TensorRT-LLM

NVIDIA, 2023 · Apache-2.0 · github.com/NVIDIA/TensorRT-LLM

vLLM and SGLang operate at the Python/CUDA runtime level. TensorRT-LLM goes deeper: it is a compiler that takes an LLM model definition and AOT (ahead-of-time) compiles it into a fused, quantized TensorRT engine — a binary artifact with hand-tuned CUDA kernels baked in. On NVIDIA hardware, especially H100, this achieves the lowest possible latency for production deployment.

TensorRT-LLM — Compilation & Serving Pipeline

Quantization — NVIDIA's Core Advantage

TRT-LLM supports the most aggressive, hardware-native quantization formats available on NVIDIA GPUs, including FP8 Tensor Cores on H100 and INT4/INT8 via GPTQ, AWQ, and NVIDIA's own SmoothQuant and QMoE techniques. Quantization both reduces memory footprint and dramatically increases math throughput (TOPS).

Quantization Precision Impact

In-Flight Batching & Paged KV Cache

TRT-LLM implements its own version of continuous batching ("in-flight batching") inside the C++ runtime, alongside a paged KV cache manager. Unlike vLLM's Python-level implementation, this happens inside a compiled C++ execution loop, adding microseconds less overhead per step — critical for latency-sensitive deployments.

GQA / MQA Optimization

TRT-LLM generates optimized kernels for Grouped-Query Attention and Multi-Query Attention used in modern models (LLaMA 3, Mistral). The compiler selects specialized CUDA implementations tuned for the exact head dimensions and group sizes of the target model.

Weight Streaming

For models larger than GPU VRAM, TRT-LLM can stream quantized INT4 weights from CPU memory to GPU during decoding, enabling serving of 70B+ models on a single A100. Combined with paged attention, this enables otherwise-impossible deployments.

LoRA at Inference

TRT-LLM compiles LoRA adapters alongside the base model, fusing them into the weight matrices at engine-build time or loading them dynamically at runtime with minimal overhead — enabling multi-tenant fine-tuned model serving on shared hardware.

Speculative Decoding

TRT-LLM supports draft-model speculative decoding with a compiled draft engine and target engine, coordinated by a Medusa-style tree verifier. All candidates are batched into a single forward pass of the target model, achieving 2–4× decode speedup.

Key trade-off: TRT-LLM achieves the best raw performance on NVIDIA hardware but requires a compile step (trtllm-build can take 10–60 minutes for large models). The compiled engine is hardware-specific. Every model update or quantization change requires a recompile. For research and fast iteration, vLLM or SGLang are faster to deploy; TRT-LLM shines in stable production with fixed models.

TL;DR Decision guide:
→ vLLM if you want a drop-in OpenAI-compatible server that works on any hardware, fast.
→ SGLang if you're building agents, multi-turn systems, or anything needing structured JSON output at scale.
→ TensorRT-LLM if you need the absolute lowest latency, are on NVIDIA hardware, and can afford the compile step.
